# EVM contracts — reading Peregrine from Ethereum

The reciprocal of Peregrine's beacon light client: this is how an Ethereum
contract learns Peregrine state without trusting a bridge operator.

> ⚠️ **Unaudited and undeployed.** Compiled, tested (41 passing Foundry tests
> including fuzzing), and Slither-clean — but never third-party reviewed and
> never on a public network. Do not put value behind it.
>
> The end-to-end test against a **real** SP1 Groth16 proof is written and wired
> (`test/PeregrineProofE2E.t.sol`) but **has not yet been run**: generating the
> proof needs Docker, which was unavailable here. It skips loudly rather than
> looking like a pass. Running it is the highest-value next step.

For the reverse direction (Peregrine verifying Ethereum), see
[`crates/peregrine-interop`](../crates/peregrine-interop).

## Design: prove off-chain, verify on-chain

Peregrine commits state with **BLAKE3** sparse-Merkle trees, and the EVM has no
BLAKE3 precompile. Verifying a Peregrine inclusion proof directly in Solidity
would cost hundreds of thousands of gas — a 256-deep SMT path makes it worse.

So the contract verifies **no Merkle paths at all**. The entire statement is
proven inside the zkVM:

```text
  guest program proves:
     a stake-weighted quorum of a SPECIFIC committee signed a checkpoint
     committing to store root R
     AND  table[key] == value  under R
  ────────────────────────────────────────────────────────────────────────
  contract verifies: one SP1 proof + reads the committed journal
```

Gas is constant regardless of proof depth, and no BLAKE3 ever runs on-chain.
The guest is the same `peregrine-interop` verification code used everywhere
else (`verify_checkpoint` + `ProvenRead::verify`), which is why the two sides
cannot drift apart.

## The three pins

A proof only means something relative to what it is a proof *of*. Three
immutable values fix that, and all three are checked on every call:

| Pin | Answers | If wrong |
| --- | --- | --- |
| `programVKey` | which program ran | a proof of a *different* program is accepted — still a perfectly valid proof, of something else |
| `committeeDigest` | whose signatures counted | a proof generated against an attacker's validator set is accepted |
| `peregrineChainId` | which network | a testnet proof applies here |

None has a setter. **An upgradeable pin is an admin key that can redefine what
every past and future proof meant**, which would make the cryptography
decorative. The cost is that changing one means a new deployment.

**Derive `programVKey` from your own build of the guest.** A verifying key
handed to you by the party who will be supplying your proofs is a program you
did not choose.

## Two rules worth knowing before reading the code

**Verification strictly precedes decoding.** The proof is checked before a
single field of `publicValues` is read. Decoding first and validating later is
how verifiers end up acting on attacker-chosen data. There is a test for the
ordering specifically, not just for "it reverts".

**Absence is not zero.** `getVerifiedValue` reverts for an unproven key rather
than returning zero — the same trap `LoadEthState` avoids in the other
direction. In both cases, "not verified" must never be mistakable for "is zero".

Six invariants are stated in the contract's NatSpec, each mapped to its test in
[`AUDIT.md`](AUDIT.md). Two more worth calling out: **equivocation reverts**
(two different roots at one Peregrine round stop the client rather than being
absorbed), and a **contradiction reverts** (a key has exactly one value under a
given root; a second, different one means the guest or the tree is broken).

## Deploying

```bash
export SP1_VERIFIER=0x...        # SP1VerifierGateway on your network
export PROGRAM_VKEY=0x...        # from YOUR build of the state guest
export COMMITTEE_DIGEST=0x...    # the validator set you verified out of band
export PEREGRINE_CHAIN_ID=1

forge script script/Deploy.s.sol:Deploy \
  --rpc-url "$RPC_URL" --private-key "$PK" --broadcast
```

The script validates every argument before broadcasting, then reads the pins
back off the deployed contract — the only check that proves the bytecode
on-chain is configured the way you intended. Pointing at an address with no code
is refused: a high-level call to a codeless address *succeeds*, so an EOA as
`SP1_VERIFIER` would silently make `verifyProof` a no-op and accept every proof.

Relaying is **permissionless**: anyone generates a Groth16 proof off-chain and
calls `verifyPeregrineState`. The proof is the authorization, so there is no
caller to trust and no access control to get wrong.

## Trust assumptions

| Assumption | Notes |
| --- | --- |
| SP1 Groth16 verifier | **Circuit-specific trusted setup** by Succinct. Unavoidable for cheap L1 verification today. |
| The three pins | See above. |
| Peregrine validator set | A 2/3 stake quorum of the pinned committee. Every signature is verified before its stake counts. |

Note the asymmetry: Peregrine verifying *Ethereum* uses SP1 **Compressed**
(STARK, **no trusted setup**). Only this direction takes the Groth16 setup, and
only because the EVM leaves no cheaper option. That is a property of the EVM,
not of the protocol.

## Known limitations

Ranked by how much they should worry you. Full discussion in
[`AUDIT.md`](AUDIT.md).

1. **Committee rotation is not implemented.** `committeeDigest` is immutable, so
   a Peregrine validator-set change requires deploying a new client. Following a
   rotating set safely means proving each transition from the previous one.
   **This is the weakest link in this direction.**
2. **No audit.**
3. **Groth16 trusted setup**, discussed above.
4. **Values are capped at 32 bytes** — refused by both guest and contract rather
   than truncated, because a truncated value is a wrong value that still looks
   well-formed.
5. **Liveness is nobody's job.** Nothing forces proofs to be submitted; a stale
   root is genuinely proven but old. `getLatestValue` returns the round
   alongside the value so callers can check.
6. **No gas-griefing analysis** under adversarial calldata.
