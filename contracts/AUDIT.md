# Audit notes — `PeregrineLightClient`

Scope, invariants, known findings, and what a reviewer should attack first.
Written for someone who has not read the rest of the repository.

**Status: unaudited.** Compiled, tested (41 passing), and statically analysed.
Never reviewed by a third party and never deployed. Do not put value behind it.

⚠️ **One gap to know before reading further:** the end-to-end test against a
real Groth16 proof is written and wired but has **never been run**. Producing
the proof requires Docker (SP1 v6 shells out to it for the gnark wrap step),
which was unavailable in the environment this was built in. So the claim "a
proof from the real prover is accepted by this contract" is **unverified** — it
is the single most valuable thing a reviewer could check first. The suite skips
that test loudly rather than letting it look like a pass.

---

## 1. What this contract is

One function does the work:

```solidity
verifyPeregrineState(bytes publicValues, bytes proofBytes) returns (bytes32)
```

It asks SP1's on-chain verifier to check a Groth16 proof, and — only if that
returns without reverting — decodes the journal the guest committed and records
`(storeRoot, table, key) → value`.

Peregrine commits state with **BLAKE3** sparse Merkle trees, which the EVM
cannot verify affordably. So the contract verifies no Merkle path at all: the
entire statement (a quorum signed store root `R`, *and* `key → value` under `R`)
is proven inside the zkVM, and gas is constant regardless of tree depth.

### Files

| File | Role |
|---|---|
| `src/PeregrineLightClient.sol` | The contract. ~290 lines, one external state-changing function. |
| `script/Deploy.s.sol` | Deployment. `deploy(...)` holds the logic; `run()` only reads env. |
| `test/PeregrineLightClient.t.sol` | 29 tests: rules, replay, equivocation, malformed input, fuzz. |

## 2. Trust model

The contract is trustless *relative to three pins*, all immutable, all checked
on every call:

| Pin | Answers | If wrong |
|---|---|---|
| `programVKey` | which program ran | a proof of a different program is accepted — it is still a valid proof, of something else |
| `committeeDigest` | whose signatures counted | a proof built against an attacker's validator set is accepted |
| `peregrineChainId` | which network | a testnet proof applies to mainnet |

None has a setter. **An upgradeable pin is an admin key that can redefine what
every past and future proof meant**, which would make the cryptography
decorative. The cost is that changing any of them means a new deployment.

### What is trusted

1. **SP1's Groth16 verifier and its trusted setup.** Groth16 needs a
   circuit-specific trusted setup, performed by Succinct. If you cannot accept
   that, this contract is not for you; there is no non-trusted-setup proof
   system cheap enough for L1 today. Peregrine's own verification of Ethereum
   uses SP1 Compressed (STARK, no trusted setup) — the asymmetry is a property
   of the EVM, not of the protocol.
2. **A 2/3 stake quorum of the pinned Peregrine committee.** The guest verifies
   every signature before its stake counts.
3. **The correctness of the guest program**, in the ordinary sense that any
   verifier trusts what it verifies. The guest calls the *same*
   `StateWitness::verify` the host runs natively, so the two cannot silently
   diverge.

### What is NOT trusted

- The submitter. `verifyPeregrineState` is permissionless; the proof is the
  authorization. There is no caller to trust and therefore no access control to
  get wrong.
- Any field of `publicValues` before the proof has been checked.
- The `ProvenRead`'s own root field (the guest uses the *signed* root instead).

## 3. Invariants

Each is stated in NatSpec on the contract and has at least one test.

| # | Invariant | Enforced by | Test |
|---|---|---|---|
| **I1** | No storage is written unless `verifyProof` returned without reverting; verification strictly precedes reading `publicValues`. | ordering in `verifyPeregrineState` | `test_RejectsInvalidProof`, `test_ProofIsCheckedBeforeJournalIsRead` |
| **I2** | `latestRound` is non-decreasing. | `StaleRound` revert | `test_RejectsStaleRound` |
| **I3** | For a given round, at most one `storeRoot` is ever accepted. | `_rootAtRound` + `ForkedRound` | `test_RejectsForkedRound` |
| **I4** | For a given `(storeRoot, table, key)`, at most one value is ever recorded. | `Contradiction` revert | `test_RejectsContradiction`, `test_ReprovingTheSameFactIsIdempotent` |
| **I5** | Reads never return an unproven value; they revert. | `UnknownValue` revert | `test_UnprovenValueReverts`, `test_ZeroIsAValidProvenValue` |
| **I6** | No ether, no owner, no pause, no upgrade path. | absence of `receive`/`fallback`/admin | `test_RejectsEther` |

**I3 is the one worth arguing about.** Two different roots at one round means a
Peregrine quorum equivocated. The contract could pick the first, pick the
highest, or stop. It stops — absorbing equivocation silently would let an
attacker who achieved it write state under a root of their choosing, and the
revert makes the event visible on-chain instead of invisible.

**I5 mirrors a rule on the Peregrine side.** `LoadEthState` traps rather than
returning zero for unverified Ethereum state; `getVerifiedValue` reverts rather
than returning zero for unproven Peregrine state. In both directions, "not
verified" must never be mistakable for "is zero".

## 4. Known limitations

Ranked by how much they should worry you.

1. **Committee rotation is not implemented.** `committeeDigest` is immutable, so
   a validator-set change requires deploying a new client. Following a rotating
   set safely means proving each transition from the previous one; this
   scaffold does not. **This is the weakest link in the Peregrine → Ethereum
   direction.**
2. **No audit.** See the status line at the top.
3. **Groth16 trusted setup**, discussed above.
4. **Values are capped at 32 bytes.** Longer values are refused by both the
   guest and the contract rather than hashed or truncated — a truncated value is
   a wrong value that still looks well-formed. Consumers needing longer values
   need a different journal shape.
5. **Liveness is not addressed.** Nothing forces anyone to submit proofs. A
   consumer reading a stale root gets genuinely proven but old data; that is why
   `getLatestValue` returns the round alongside the value, and why callers
   should check it.
6. **No gas griefing analysis under adversarial calldata.** Proof size is
   bounded by SP1's Groth16 encoding, but this has not been measured against a
   hostile submitter.

## 5. Static analysis

`slither src/PeregrineLightClient.sol --exclude-dependencies`. Results and
dispositions are in [`SLITHER.md`](SLITHER.md), which records every finding
including the ones deliberately not fixed, with reasons.

Notes on detectors that commonly fire on contracts shaped like this one:

- **`solc-version`** — the pragma is `^0.8.28`, above the 0.8.20 threshold where
  `PUSH0` becomes an issue on chains that have not adopted Shanghai. Deploying
  to such a chain requires setting `evm_version` accordingly.
- **`abi-encodePacked-collision`** — `_slot` uses `abi.encodePacked` on three
  `bytes32` operands. Fixed-width only, so the concatenation is unambiguous and
  no collision is reachable. It would *not* be safe if any operand were dynamic.
- **`reentrancy-*`** — the only external call is a `view` on an immutable,
  code-checked address, made before any state write. There is no value transfer
  and no callback surface.
- **`low-level-calls`** — none in `src/`. Present in tests only.

## 6. Where to attack first

If you have limited time, in this order:

1. **The journal encoding.** Rust hand-writes eight 32-byte words; Solidity
   `abi.decode`s them. A silent disagreement shifts every field — a `round`
   read as a `chainId` — and nothing would fail loudly.
   `test/PeregrineJournalAbi.t.sol` pins this against a Rust-generated fixture;
   check the fixture is actually regenerated in CI and not stale.
2. **The ordering in `verifyPeregrineState`.** Everything rests on
   verify-before-decode. A refactor that moves the decode up is not obviously
   wrong to a reader.
3. **The guest.** The contract cannot be stronger than the statement it
   verifies. Read `crates/peregrine-interop/src/state.rs` and ask whether
   anything in the journal is *copied* from the witness rather than *derived* by
   verification.
4. **The equivocation and staleness rules**, for a replay this contract accepts
   as fresh.

## 7. Reproducing

```bash
cd contracts
git submodule update --init --recursive   # or: forge install
forge build
forge test -vv                            # 41 tests, incl. fuzz

# Regenerate the cross-language fixture (also runs in CI):
cd .. && PEREGRINE_WRITE_FIXTURES=1 \
  cargo test -p peregrine-interop --test state_journal
```

The end-to-end test against a real Groth16 proof is separate and slow; see the
README's proving section.
