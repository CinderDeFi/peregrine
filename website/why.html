Why Peregrine

verify, don't trust — at every boundary

Blockchains are good at ordering and bad at data. That gap is where most of the industry's trust quietly leaks back in, and Peregrine is an attempt to close it in three specific places.

Peregrine is an unaudited bootstrap scaffold. It has never been deployed, holds no value, and has no token. What follows is an argument about design, supported by measurements you can reproduce — not a claim that it is ready to run anything real.

1. Reads are trust-me, and nobody says so

A blockchain's guarantees are real up to the node boundary. Past it, almost every application asks an RPC provider what the state is and believes the answer. Your users' security ends wherever that provider's integrity does.

Peregrine keeps state in sparse Merkle trees, and every read comes with an inclusion proof. A client holding a 32-byte root verifies the value itself — in a browser, with no node to trust: 

const read = provenReadFromJson(await res.json());
if (!verifyProvenRead(read, trustedStoreRoot)) {
  throw new Error("the node lied");
}

That verifier is written independently of the node, in TypeScript, and is checked against Rust-generated fixtures in CI so the two implementations cannot silently drift apart. A light client that verifies differently from the chain is worse than no light client at all.

2. High-frequency data doesn't fit in a block

Price ticks, sensor readings, and telemetry arrive continuously. Blocks designed for financial settlement are the wrong shape for them, so the data gets pushed off-chain into exactly the oracles the chain was supposed to replace.

Peregrine carries signed records inside consensus dissemination rather than queueing them behind blocks. They commit to a deterministic total order and materialize into queryable, provable tables. Measured on four validators on a single laptop:

Loopback has no wide-area round-trip, so treat the latency as a floor rather than a finality claim. Reproduce any row with peregrine bench.

3. Bridges are where the money goes missing

Most cross-chain systems are multisigs wearing a cryptography costume: a committee attests that something happened on another chain, and you trust the committee. The historical loss record speaks for itself.

Peregrine verifies Ethereum state inside a zkVM, and every validator re-checks the proof at commit time — so acceptance is part of the state transition, not something a relayer is trusted to have done. The guest program's image is pinned, because a valid proof of a different program is still a valid proof of something else.

A real proof of Ethereum state verifies inside the commit path in 52 ms. Proving takes minutes and happens once, off-chain, by whoever wants the claim believed. Verification is milliseconds and happens on every validator. That asymmetry is the whole design.

It is tested against real mainnet data rather than hand-written vectors: reproduced block hashes, real eth_getProof responses, and a real 510-of-512 BLS aggregate signature.

The rule underneath all of it: absence is never zero

A Peregrine contract that reads unverified Ethereum state does not get 0 — the transaction traps. An on-chain read of a key that was never proven does not return 0 — it reverts.

This sounds pedantic until you notice how many real exploits are a system confusing "I have no data" with "the value is zero": an under-collateralised loan marked healthy because a balance read as zero, an oracle outage priced as a crash. Missing data is an error. Making that impossible to ignore is worth more than most features.

What we are not claiming

Peregrine has not been audited, deployed, or economically modelled. Equivocation is detected but not slashed. RPC rate limiting bounds one connection and is not Sybil resistance. Committee rotation for the Ethereum-side client is not implemented.

The full list lives in AUDIT.md, it is ranked by how much it should worry you, and it is longer than this page. That is deliberate: a project asking you to verify rather than trust should be the first to publish what it cannot yet prove.
